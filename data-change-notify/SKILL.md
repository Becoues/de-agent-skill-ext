# 数据变更周知判定

上游业务库的数据会被同步进数据仓库，再层层加工成看板、财务报表和对外材料。数据管线的故障**绝大多数是静默的**——它很少报错，更常见的是安静地算出一个看起来正常的错数字。

你的任务：把手上的改动归到 L0 / L1 / L2，只在 L1 / L2 时产出一段周知文案。

## 判定原则

按**「数据团队能不能自己发现」**分层，不按改动类型分层。落在「必须周知」那一格的，都是技术上无法察觉的。

**不确定属于哪一层时，一律按需要周知处理。** 漏报的代价远大于多说一句。

## L0：不用周知

数据团队的入湖作业会自动吸收。

- 新增字段
- 新增或调整索引
- 不改变表结构和字段含义的内部重构

例外——下面两种不是 L0：

1. **新增字段用于替代旧字段**：本质是改名，按 L1 处理。
2. **新增字段是不常见类型**（`numeric`、`jsonb`、`uuid`、枚举、数组等）：入湖的类型映射通常只覆盖基础类型，其余会静默落成字符串。如果下游要对该字段做数值计算或结构解析，顺口提一句类型即可。

## L1：提前说一句

数据团队能发现，但通常滞后一天，那一天的下游数据已经是错的。

- **删除字段**
- **字段改名**（等于删一个加一个，旧名字会留在数仓里继续被读，两边都不报错）
- **字段改类型**
- **某列停止写入**：功能下线、开关关闭、默认值改动。表结构和行数都正常，只有值悄悄没了，任何基于 schema 的检查都发现不了。
- **停写老表 / 双写切换 / 表改名**：老表行数归零，数仓里的表看起来还在、只是不再更新，下游继续拿旧数据算。

## L2：必须周知

数据团队**无论加多少监控都发现不了**，因为数据在技术上完全正常，只是含义不对了。不说就是静默污染。

- **字段含义变了但类型没变**：金额单位从分改成元、枚举值含义变化、时间戳时区变化。类型、行数、空值率全部正常。这类改动会直接把收入、留存、转化率算错，且错得很像真的。
- **主键或唯一性语义变了**：增量同步靠主键去重合并，语义一变会静默产生重复行或互相覆盖。
- **回填或修正历史数据**：增量同步只拉当天变更，历史行被改了永远追不上，数仓会和源库长期不一致且没有任何信号。**这一条最容易漏——修数据时通常没人想到要说。**
- **新增表**：新表不会自动进数仓，数据团队连它存在都不知道，无从发现缺失。需要入仓请直接提需求。
- **软删改硬删**：行直接消失。增量合并模式下数仓里的旧行永远删不掉，会一直被当有效数据统计。
- **已有表新增了写入方**：另一个服务开始往同一张表写、口径不同。数据长得一样，混在一起无法区分。

## 输出格式

判定为 L1 / L2 时，产出下面这段并告诉用户可直接复制发送。**不要自动发送。**

```
【数据变更周知】
库.表：<库名 / schema.表名>
变更内容：<一句话说清改了什么>
层级：<L1 或 L2>
生效时间：<已生效的写实际时间；未上线的写计划时间>
影响范围：<下游会看到什么现象>
是否可回滚：<能否回滚；已产生的数据影响能否自动恢复>
联系人：<你>
```

含义变更类（L2）请额外附一行「改前 / 改后」对照，例如 `amount: 分 → 元`。

判定为 L0 时，只回一句「这个改动不需要周知数据工程」，不要展开解释，不要产出文案。

## 边界

- **只提醒，不阻断。** 不要因为这个判定拒绝提交或修改用户的代码。
- **不自动发消息。** 文案交给用户，发送与否由用户决定。
- 不要猜测具体的下游表名或负责人；不确定就写「待数据工程确认」。
